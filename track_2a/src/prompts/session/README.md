# German hybrid prompts (v9)

German sessions now use six `hybrid_*.de.txt` tasks: analysis extracts quotes/intent; speaker handles a controller-approved acknowledgement or clarification; company selects explicit source facts; evaluator assesses criterion-scoped evidence in small groups; learning supplies one exercise/reflection; revision compares a new answer with its learning target. No demonstrations are injected. Code supplies conservative support fallback, question progression, literal evidence checks, source-fact rendering, unassessed explanations and visible citations. Saved learning targets are context for later sessions, never evidence about a new answer.

The six German fixed-context comparisons use the same 77 v8 answers and original preceding conversations. All labels remain drafts. Literal evidence and fact IDs improve traceability but do not guarantee meaning, completeness or useful learning targets. See the technical report for results.

## Earlier v8 pipeline (English/French/Italian)

The controller uses three small tasks in the session language: `analysis`, `speaker`, and final `feedback`. German, French and Italian use `.de.txt`, `.fr.txt` and `.it.txt`; English uses the unsuffixed files. Previous `interviewer*` files are preserved but no longer invoked by the controller.

`analysis*` now runs on every accepted interview answer, including introductions and closing. It sees the actual question, stage/subtype, latest answer, dialogue and evidence records. It extracts at most three facts with exact latest-answer quotes, answered/partial/unanswered status, one essential gap, an exact strong-self-doubt quote when present, and whether the candidate asks for company information. Ordinary nervousness is not a distress referral trigger. Prior record IDs may be linked as clarified or potentially conflicting only with newly quoted evidence. IDs and quotes are validated; their presence does not prove semantic correctness.

`examples.<language>.json` contains assistant-adapted demonstrations inspired by organiser T-02/T-03 and F-11, in the selected language. Analysis receives two stage-relevant demonstrations plus a gap-resolution demonstration when memory contains open gaps. Speaker receives one action-specific demonstration. Examples are explicitly fictional and cannot be used as evidence about the real candidate. They demonstrate sufficient short answers, targeted clarification, company requests and support. No reference scores or recap examples are injected. These development scenarios are not an independent held-out benchmark.

Code owns progression. Strong self-doubt selects `support_advance`; a real company-information request selects `answer_company`, including during phone-document questions. Otherwise a follow-up requires a partial/unanswered answer, a nonempty essential gap, another planned question and no previous follow-up. Planned main questions and previously asked questions cannot be copied as follow-ups. Existing bank plans are retained for this experiment; shortening and skipping redundant main questions are not yet implemented.

`speaker*` receives the permitted action, validated analysis, public posting, next bank question, dialogue and evidence records. It must offer a short contextual acknowledgement or bridge instead of bare questions on advance, without competence praise or invented traits. Normal acknowledgement is at most 35 words, support 60, company answers 80; follow-up questions are at most 35. Company answers must answer the request or state what information is unavailable. Code appends the exact next bank question. Only ordinary closing can use fixed thanks. Invalid output uses a neutral bank fallback, with a fixed supportive message if a validated distress quote exists.

Evidence records retain record/turn IDs, stage/subtype topic, quoted facts, open gaps, clarification links and possible-conflict links. Resolving a gap preserves its original text and quotes. Potential conflicts are tentative, never labels of dishonesty. Failed analysis records its unavailability without fabricated evidence. The records are saved in sessions but are not supplied to the recap task yet.

`feedback*` is unchanged by this decomposition. It receives the actual whole transcript and public eleven-criterion rubric plus all 26 feedback guidelines from `guidance.<language>.json`. German/English descriptions derive from supplied resources; French/Italian translations need validation. Required candidate excerpts are constrained and checked, but their presence does not establish sound interpretation. Internal quotes are still not shown in the delivered recap, a known concreteness limitation.

`instructions.json` supplies localised fixed responses, task labels and correction requests. Technical JSON keys and state enums remain stable. Source company facts and candidate excerpts retain their original wording.

Each model task permits one correction. Code counts all attempts, reserves two calls for final feedback and caps session requests at `5 × accepted answers − 1`. Unavailable analysis is bypassed rather than invented; inadequate budget or speaker validation uses a bank fallback. Feedback and transport failures are reported. No live judge is used.

The v7 development run completed all 28 organiser scenarios (20 German, 5 French, 3 Italian), with 728 coach calls for 420 answers: 1.73 per answer, highest session average 1.94. Of the 28 assistant-authored whole-session reviews, two are now validated and 26 remain drafts; ten are highlighted for user validation. English and consumer-hardware VRAM remain unmeasured. See the [technical report](../../../technical_report.md).

The v8 warmth/memory run completed the same ten highlighted scenarios with 135 answers and 290 coach calls (2.15 per answer; maximum session average 2.54). Reviews remain drafts. The model often copies demonstration wording, misses company requests and strong self-doubt, and produced no clarification/conflict links. Quotes and eligible IDs are mechanically validated; adaptive quality is not established. Recap and question-plan length remain unchanged.
